S-001 · High · Unverified tenant identity — any caller can act as any tenant

Standard
A01:2025 · A07:2025 · API1:2023 · API2:2023 · CWE-639 · CWE-290 · ASVS V8.2.2, V8.3.1
Location
src/api/routes/v1/_common.py:13-22; exposure: docker-compose.yml:10-11, server_run.py:19
Evidence
owner = (x_owner_id or "").strip() — the header value is the identity. Nothing proves the request came through the gateway; compose publishes the port on all host interfaces.
Impact
Any client that reaches the port directly (same network, misrouted ingress, another internal service) sets X-Owner-Id to another tenant's id and can list, read (including webhook credentials, S-004), edit, trigger or delete that tenant's schedules. Tenant ids are often guessable. Rated High because the repo's deployment publishes the port; drops to Medium if the port is provably reachable only by the gateway.
Fix
Make the service verify the gateway, not trust the header. Smallest step: a shared gateway secret checked in constant time, fail closed when unset in production. Better: verify a gateway-signed JWT (pinned alg, exp/aud/iss) and take the owner from its claim. Also bind the published port to an internal interface or remove ports: and use a private network.
Status
open
Client (any) → X-Owner-Id header no proof of gateway → current_owner() → Other tenant's schedules

S-002 · High · SSRF guard bypass (check-then-connect, incomplete ranges) with response read-back

Standard
A01:2025 (SSRF) · API7:2023 · CWE-918 · CWE-367 · ASVS V1.3.6
Location
src/scheduling/actions.py:127-141 (guard), :71 and :77 (check, then a second resolution inside httpx), :106-108 (notify, same pattern)
Evidence
(1) _assert_safe_url resolves the host with getaddrinfo, then client.request(..., url) resolves it again. A hostname whose DNS answer changes between the two lookups (short TTL) passes the check and connects to an internal address.
(2) if ip.is_loopback or ip.is_private or ip.is_link_local or ip.is_reserved lets through 100.64.0.0/10 (shared/CGNAT, used for internal endpoints by some clouds) and multicast — verified on Python 3.12.3.
(3) The target's response body is stored (jobs.py:43) and returned by GET /schedules/{id}/runs, and the blocked-target error text names the resolved internal IP (actions.py:141), which is stored in last_error.
Impact
A tenant (or, with S-001, anyone) makes the service call internal HTTP services or cloud metadata endpoints and reads up to 2048 characters of each response back through the runs API. Retries and interval triggers repeat the request.
Fix
Resolve once and connect to the vetted IP: a custom httpx transport / httpcore network backend that checks every resolved address with not ip.is_global at connect time; or route all outbound calls through an egress proxy that enforces the deny list. Block on not ip.is_global (covers CGNAT, multicast, documentation, benchmarking ranges). Do not echo the resolved IP in the error.
Status
open
ScheduleCreate.action.url → _assert_safe_url (DNS lookup 1) no IP pinning → httpx (DNS lookup 2) → Internal service / metadata → response_body via GET /runs

S-003 · Medium · No resource limits — service usable as an outbound traffic relay

Standard
API4:2023 · API6:2023 · CWE-770 · CWE-400 · ASVS V2.4.1
Location
src/scheduling/triggers.py:111 (interval args passed through), src/core/db/db_schema.py:50-52 (timeout ≤ 300 s, retries ≤ 10), src/core/db/db_schema.py:105 (unbounded payload), src/scheduling/schedule_service.py:22 (no per-owner quota), src/scheduling/schedule_service.py:32 (unbounded list)
Evidence
armable_trigger accepted {"seconds": 0.01} (verified). No cap on schedules per owner, request body size, payload size, or list length; no rate limit on any route.
Impact
One caller creates many schedules firing every few milliseconds at a third-party URL, each with up to 11 attempts — the service (and its IP reputation) becomes a traffic source against that target, and scheduler/DB load starves other tenants. Large payloads bloat MongoDB and every list response.
Fix
Minimum interval (e.g. 60 s, configurable) for interval and cron; per-owner schedule cap; payload size cap; request body size cap; paginate GET /schedules like /runs; rate-limit create and run-now at the gateway.
Status
open

S-004 · Medium · Webhook credentials stored in clear and returned on every read

Standard
API3:2023 · A04:2025 · CWE-200 · CWE-312 · ASVS V14.2.1
Location
src/api/models/schedule.py:124 (action: WebhookAction | None in ScheduleRead), src/core/db/db_schema.py:49
Evidence
ScheduleRead serialises the full WebhookAction, including headers, which is where callers put Authorization / API-key values for the target.
Impact
Every GET, list, create, update, pause, resume and run response echoes the target's credentials; they land in client logs, browser devtools, gateway logs, and (with S-001) any other tenant's hands. At rest they sit in clear in MongoDB and backups.
Fix
Return header names with masked values in reads (write-only secret). Optionally encrypt header values at rest.
Status
open
# src/api/models/schedule.py — ScheduleRead
+    @field_serializer("action")
+    def _mask_headers(self, action: WebhookAction | None):
+        if action is None:
+            return None
+        data = action.model_dump(mode="json")
+        data["headers"] = {k: "***" for k in action.headers}
+        return data

S-005 · Medium · Sensitive data written to logs, run records and notify callbacks

Standard
A09:2025 · CWE-532 · CWE-209 · ASVS V16.2.5
Location
src/scheduling/actions.py:56, :61, :64, :86, :112; propagated via src/scheduling/jobs.py:44 and actions.py:101
Evidence
logger.info("... payload=%s", schedule.id, schedule.payload) logs the full tenant payload at INFO.
f"{action.method} {url} failed: {exc}" embeds the full URL (query-string tokens, userinfo) and httpx's message (which repeats the URL). That string goes to logger.exception (with traceback), last_error, ScheduleRun.error, and the notify body sent to a third party.

Fix
Never log payload. Build error text from scheme + host + path only. Use logger.warning(..., exc_info=False) for expected delivery failures; keep exception for unexpected ones.

S-006 · Medium · No security event logging, no request correlation

Standard
A09:2025 · CWE-778 · CWE-117 · ASVS V16.3.1, V16.3.2, V16.2.1
Location
src/core/logging/logger.py:12-35, src/core/exceptions.py:68-70 (AppError handler logs nothing), server.py:41-55 (no request middleware)
Evidence
401s, 404s on foreign ids, 409s and 422s return without a log line. No request id is generated or propagated, so a 500's logger.exception("Unhandled error") cannot be tied to a request, owner or route. Plain-text format: any future log line with user text can forge lines (CWE-117). Granian access log is off by default.
Impact
Tenant-id guessing (S-001), id enumeration and abuse (S-003) leave no trail; incident response cannot reconstruct who did what.
Fix
One middleware: accept or mint X-Request-ID, return it, log one line per request (method, route template, status, owner id, duration, request id). Log AuthError at WARNING. JSON formatter (or %r for user strings) to neutralise newlines.
Status
open
# server.py — in create_app
+    @app.middleware("http")
+    async def _access_log(request, call_next):
+        rid = request.headers.get("x-request-id") or uuid.uuid4().hex
+        started = time.perf_counter()
+        response = await call_next(request)
+        route = request.scope.get("route")
+        logger.info("request id=%s %s %s status=%d owner=%r ms=%.1f",
+                    rid, request.method, getattr(route, "path", "-"), response.status_code,
+                    request.headers.get("x-owner-id"), (time.perf_counter() - started) * 1000)
+        response.headers["X-Request-ID"] = rid
+        return response
# ponytail: one log line per request; add contextvar-based request id in all logs when needed.

S-010 · Info · X-Owner-Id unbounded; legacy default owner "public"

Standard
API4:2023 · CWE-20 · ASVS V2.2.1
Location
src/api/routes/v1/_common.py:19, src/core/db/db_schema.py:89
Evidence
Any non-blank string (up to the server's header limit, any characters) becomes owner_id and is stored and indexed. Legacy documents default to "public", so any caller sending X-Owner-Id: public owns them.
Fix
Validate the header (e.g. ^[A-Za-z0-9_.:-]{1,128}$); migrate legacy "public" documents to a real owner or reject that value.
Status
open
